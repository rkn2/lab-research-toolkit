# Reproducible Research

The [offboarding checklist](phd-milestones.md#lab-offboarding-data-and-file-handoff) asks you to hand over "everything needed to rerun your results" when you graduate. Most students read that at the end of their PhD and panic. This guide is how you make it a non-event: if you work reproducibly from day one, offboarding is just zipping up folders you already kept clean.

Reproducibility is not bureaucracy. It is the difference between a result you can defend and a result you merely remember getting. If you cannot rerun an analysis and get the same number, you do not actually know that number is right — and neither does anyone reading your paper.

## The One Rule

**Everything that is a result must be regenerable by running code, from raw data, without manual steps.**

If any number, figure, or table in your paper exists only because you once clicked something in a GUI, edited a spreadsheet by hand, or ran cells in a particular order you no longer remember — that result is not reproducible, and it is one lost laptop away from being gone. The whole discipline below exists to serve this one rule.

## Project Structure

Adopt a consistent folder layout for every project. A common, sane one:

```
project-name/
├── README.md            # what this is, how to run it
├── requirements.txt     # or environment.yml — the exact software needed
├── data/
│   ├── raw/             # original data, READ-ONLY, never edited
│   └── processed/       # generated by code from raw/ — safe to delete and regenerate
├── src/                 # scripts and modules
├── notebooks/           # exploration; promote finished analysis to src/
├── results/
│   ├── figures/         # generated by code
│   └── tables/          # generated by code
└── .gitignore
```

The load-bearing ideas:

- **`data/raw/` is sacred and read-only.** You never edit raw data by hand. If it needs cleaning, a script reads `raw/` and writes `processed/`. This means you can always trace any result back to untouched source data.
- **Anything in `processed/`, `figures/`, or `tables/` should be deletable.** If you deleted that folder and re-ran your code, you would get it back identically. If you would not, something is being done by hand that should be in a script.
- **Exploration lives in notebooks; results live in scripts.** Notebooks are wonderful for figuring things out and terrible for reproducibility — they run out of order, hold hidden state, and rot. Once an analysis is real, move it into a `.py` script in `src/` that runs top to bottom.

## Environments

"It works on my machine" is a bug, not a defense. Your code depends on specific versions of specific libraries, and those change.

- **Use an isolated environment per project.** `conda` (via Miniconda) or Python's built-in `venv` both work. Never install project dependencies into your system Python.
- **Record your dependencies in a file** that lives in the repo:
  - conda: `conda env export > environment.yml`
  - pip: `pip freeze > requirements.txt`
- **Someone should be able to recreate your environment in one command:**
  - `conda env create -f environment.yml`
  - `pip install -r requirements.txt`
- **Pin versions when a result depends on them.** A different version of a library can silently change a numerical result. If your findings depend on exact numbers (they do), pin the versions.

This is the single most common reason a graduated student's code will not run a year later. Solve it now, for free, by keeping the environment file current.

## Data Provenance

Provenance is the documented chain from raw data to final result. For every dataset you use:

- **Record where it came from.** URL, download date, version, and who collected it. Put this in the README or a `data/raw/SOURCES.md`. See [Finding Data](finding-data.md) for the lab's common sources.
- **Never manually edit raw data.** Every transformation — cleaning, filtering, joining, feature engineering — happens in code that reads `raw/` and writes `processed/`. This way the transformation is inspectable and repeatable.
- **A result you cannot trace back to raw data does not exist.** If you cannot say exactly which rows were dropped and why, you cannot defend the result to a reviewer or a committee.

## Pitfalls Specific to Machine Learning

If your work involves training models — damage classification, vulnerability prediction, anything with a train/test split — reproducibility failures become correctness failures. These bugs do not crash; they quietly inflate your performance and get caught in review, or worse, after publication.

- **Train/test leakage.** The cardinal sin. Any information from your test set that touches your training process — fitting a scaler on the full dataset before splitting, selecting features using all the data, tuning hyperparameters on the test set — leaks. Fit every transformation on the training set only, then apply it to the test set. When in doubt, split first, then do everything else.
- **Target leakage.** A feature that secretly encodes the answer. If a feature would not be available at prediction time in the real world, it does not belong in the model. A damage label baked into a "notes" field, a post-event measurement used to predict the event — these produce spectacular accuracy and worthless models.
- **Evaluate once.** Your test set is a one-time resource. Every time you look at test performance and then change your model, you have leaked a little information and your reported number gets a little more optimistic. Develop against a validation set; touch the test set once, at the end.
- **Control randomness.** Set and record random seeds for splits, initialization, and any stochastic step, so a rerun reproduces the result. But also — report whether your result survives a *different* seed. A finding that only holds for `seed=42` is not a finding.
- **Watch for grouped data.** If you have multiple rows per building, per event, or per site, a naive random split can put the same group in both train and test — another leak. Split by group, not by row.

When a result looks too good, assume leakage until you have ruled it out. That instinct will save you from the most painful correction a young researcher can face. If a pipeline's numbers seem off or suspiciously strong, stop and trace the data flow before trusting them — check with Rebecca early rather than building on a result you cannot yet explain.

## The README

Every project folder has a README that lets a stranger — including future you — run it. At minimum:

1. **What this project is** — one paragraph.
2. **How to set up the environment** — the one command from the [Environments](#environments) section.
3. **How to run it** — the sequence of scripts, in order, that reproduces the results. Ideally a single `run_all` script or a numbered list.
4. **Where the data comes from** — sources and how to obtain the raw data if it is not in the repo.
5. **What to expect** — which figures and tables get generated and where they land.

If your README passes the "cold start" test — a new lab member could clone the repo and reproduce Figure 3 without asking you anything — you are done. That is also exactly what the offboarding checklist requires.

## A Reproducibility Checklist

Run through this before every paper submission and every committee meeting:

- [ ] Raw data is unmodified and its source is documented
- [ ] Every figure and table in the paper is generated by code, not by hand
- [ ] Deleting `processed/` and `results/` and re-running reproduces them identically
- [ ] The environment is captured in `requirements.txt` or `environment.yml`
- [ ] Random seeds are set and recorded; key results survive a different seed
- [ ] For ML work: transformations are fit on train only; the test set was evaluated once; no feature leaks the target
- [ ] A README explains how to reproduce the results from a cold start
- [ ] Code is in a git repository (see [Git and GitHub](git-and-github.md))
